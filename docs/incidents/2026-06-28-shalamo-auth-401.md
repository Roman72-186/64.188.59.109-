# Инцидент 2026-06-28 — shalamo HTTP 401, оплачено-без-тега

**Статус:** закрыт · **Severity:** высокий (клиенты оплатили, доступ не получили)
**Канал оплаты:** все (тег — общий гейт доступа для tbank/dolyame/tbank_credit)

## Кратко (вывод)

shalamov.io **сменил способ авторизации API без предупреждения**: токен теперь
принимается только заголовком `Authorization: Bearer <key>`, а боевой `config.yaml`
слал его query-параметром `?api_token=<key>`. Все `assign_tag` стали падать с
`HTTP 401 {"error":"unauthorized"}` → тег не назначался → **доступ не выдавался**.
Проблему заметили **вручную** спустя ~12 часов; за это время застряло 4 оплаченных
заказа (≈48 600 ₽).

Два усугубляющих фактора:
1. query-режим был **нештатным переопределением** дефолта `ShalamoAuth` (в коде
   дефолт уже `Bearer`) — то есть конфиг отклонялся от кода без необходимости.
2. **Не было ни авто-восстановления, ни сигнала тревоги** по «оплачено, но тег не
   назначен». Синхронная модель (PRD §7.8) на 401 бесполезна (ретраи Т-Банка
   быстро истекают; Долями/кредит webhook не повторяют), а единственная страховка
   (`grant_access` на повторном `/init-payment`) срабатывает, только если клиент сам
   заново откроет оплату. Мониторинга не было — только логи, которые никто не читал.

## Диагностика

Замена значения ключа НЕ помогала (и старый, и новый токен → 401), значит дело не в
значении. Перебор способов передачи токена к `attachTagToContact` на dummy-контакте
`0` (никого реального не задели, смотрели только коды):

| Схема | Ответ |
|---|---|
| `?api_token=` (как было в конфиге) | 401 unauthorized |
| **`Authorization: Bearer <key>`** | **404 «Contact not found»** ← auth прошла |
| `Authorization: Token …` | 401 |
| `X-Api-Key` | 401 |
| `?token=` / `?api_key=` | 401 |

`404 Contact not found` = авторизация принята (дошло до поиска контакта). Значит ключ
валиден, изменился только транспорт токена.

## Фикс

В `/opt/tbank_proxy/config.yaml`, блок `shalamo.auth`:

```yaml
auth:
  in: header                          # было: in: query
  header: Authorization               # было: param: api_token
  value_template: 'Bearer {api_key}'  # было: '{api_key}'
```

(= дефолт `ShalamoAuth` в `app/config.py`.) Затем `systemctl restart tbank-proxy` и
ручной догон застрявших: для каждого `paid_at IS NOT NULL AND tag_assigned_at IS NULL`
вызвали существующий `grant_access` → `assign_tag` (HTTP 204) → `mark_tag_assigned`.

## Меры на будущее (реализовано)

1. **Авто-реконсилятор тегов** — фоновая задача `_retry_stranded_tags` (`app/main.py`,
   по образцу `_fiscalize_pending`), переиспользует `grant_access`. Периодически
   (`shalamo.reconcile_interval_seconds`) добивает «оплачено, но тег не назначен»
   через `database.get_paid_untagged_orders`. После восстановления shalamo застрявшие
   заказы рассасываются **сами**, без ручного скрипта.
   *Гейт от двойной авторассылки:* `atomic_capture` не даёт взаимного исключения
   между одновременными назначателями (возвращает True, пока `tag_assigned_at IS NULL`),
   поэтому при восстановлении shalamo webhook-ретрай Т-Банка и реконсилятор могли бы
   оба вызвать `assign_tag` по одному заказу → две авторассылки. `grant_access`
   обёрнут в `asyncio.Lock` + повторная проверка `tag_assigned_at` под локом —
   второй путь видит уже назначенный тег и shalamo повторно не дёргает.
2. **Сигнал тревоги (логи)** — если оплаченный заказ висит без тега дольше
   `shalamo.stranded_alert_after_seconds`, реконсилятор пишет агрегированный
   `CRITICAL` (`grep CRITICAL logs/app.log`). Push-канал (Telegram/email) — отложен.
3. **Деградация `/health`** — при наличии застрявших отдаёт
   `{"status":"degraded","stranded":N}` (HTTP 200), чтобы внешний uptime-монитор мог
   ловить такое без push-инфраструктуры.
4. **Пример конфига** (`config.example.yaml`) приведён к Bearer-схеме, чтобы новые
   развёртывания не повторяли нештатный query-режим.
